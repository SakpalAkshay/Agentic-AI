## 2. Chatbot Design — A Single-Node Sequential Workflow

A chatbot is essentially a very simple LangGraph workflow — **sequential, with just one node**:

```
START → chat_node → END    (run in a loop while the user is chatting)
```

**Flow:** the user sends a message → it goes to `chat_node` (which contains an LLM) → the LLM generates a reply → the reply goes to END. Repeat for every user message.

The interesting question is **what should the state contain?**

> In a chatbot, the data that matters is the **messages exchanged** between the user and the LLM. So the state will hold a **list of messages**.

Every back-and-forth (user question, LLM reply, user follow-up, LLM reply, …) gets appended to that list. The state holds the **entire conversation history**.

---

## 3. Defining the State — `BaseMessage` + `add_messages`

Two important details when defining the state for a chatbot:

### Use `BaseMessage` instead of `str`

In the LangChain playlist, four message types were covered: `HumanMessage` (typed by the user), `AIMessage` (generated by the LLM), `SystemMessage` (to specify a role), and `ToolMessage`. **All four inherit from `BaseMessage`.**

By typing the list as `list[BaseMessage]`, you allow any of these message types into the conversation history — much more flexible than plain strings.

### Use the `add_messages` reducer

By default in LangGraph, when a node writes to a state key, the **previous value is replaced**. For a chatbot this is fatal — every new message would overwrite the conversation history.

In the parallel-workflows video, the fix was `Annotated[list[int], operator.add]`. Here we use a **specialized built-in reducer** designed for messages:

```python
from langgraph.graph.message import add_messages
```

> `add_messages` works like `operator.add`, but it's optimized for working with `BaseMessage` objects. Whenever you append messages to a list in LangGraph, **use `add_messages` instead of `operator.add`** — it's the recommended approach.

## 4. Building the Chatbot — Full Code

Create a new file (e.g., `basic_chatbot.ipynb`):

```python
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain_openai import ChatOpenAI
from langchain_core.messages import BaseMessage, HumanMessage
from typing import TypedDict, Annotated
from dotenv import load_dotenv

load_dotenv()

# ---------- The LLM ----------
llm = ChatOpenAI()


# ---------- Define the State ----------
class ChatState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]


# ---------- The Single Node ----------
def chat_node(state: ChatState):
    # 1. Extract the conversation so far
    messages = state['messages']

    # 2. Send it to the LLM
    response = llm.invoke(messages)

    # 3. Return the new AI message wrapped in a list
    #    (the add_messages reducer will append it to the history)
    return {'messages': [response]}


# ---------- Build the Graph ----------
graph = StateGraph(ChatState)
graph.add_node('chat_node', chat_node)

graph.add_edge(START, 'chat_node')
graph.add_edge('chat_node', END)

chatbot = graph.compile()
```

Try one invocation:

```python
initial_state = {
    'messages': [HumanMessage(content='What is the capital of India?')]
}

result = chatbot.invoke(initial_state)
print(result)
```

The returned state contains a `messages` list with both the original `HumanMessage` and the new `AIMessage` (`"The capital of India is New Delhi"`). To extract just the answer:

```python
answer = result['messages'][-1].content
print(answer)
```

> Notice we wrap the response in a list — `{'messages': [response]}`. The `add_messages` reducer then **appends** it to the existing history rather than replacing it.

## 5. Adding a Chat Loop — Feels Like a Real Chatbot Now

The above runs once. To actually *chat*, wrap it in a `while` loop that runs until the user types `exit`, `quit`, or `bye`:

```python
while True:
    user_message = input('Type here: ')
    print('User:', user_message)

    # exit condition
    if user_message.strip().lower() in ['exit', 'quit', 'bye']:
        break

    response = chatbot.invoke({
        'messages': [HumanMessage(content=user_message)]
    })

    print('AI:', response['messages'][-1].content)
```

This feels like a proper chatbot (without a UI — just typing in the console). **But there's a big problem.**

## 6. The Problem — The Chatbot Has No Memory

Try this:

```
User: Hi, my name is Nitish.
AI:   Hello Nitish, how can I assist you?

User: Can you tell me my name?
AI:   I'm sorry, but I don't have access to your personal information.
```

The chatbot has become **Aamir Khan from Ghajini** — it remembers nothing. Even simple chained math fails (`Add 10 to 100` → `110`, then `Add 15 to the result` → `25`).

**Why?** Pause and think — the answer is *not* obvious. The state has the `add_messages` reducer, so why is history being lost?

> **The cause:** Every iteration of the `while` loop calls `chatbot.invoke(...)` **fresh**. Every `invoke` starts a brand-new workflow execution. The state begins from scratch with only the message you passed in — *the previous run's state has been thrown away*. The `add_messages` reducer works **within a single run**, not across runs.

So when the user types "Can you tell me my name?", the LLM only sees that single message — it never saw "Hi, my name is Nitish" from the previous invocation.

**Technically the code is correct** — but every `invoke` starts the state from scratch, which erases all previous context.

---

## 7. The Fix — Persistence with a Checkpointer

The fix uses a LangGraph concept called **persistence**.

> **The idea:** When workflow execution reaches END, instead of letting the state be erased, **save it somewhere** so the next `invoke` can resume from where it left off.

**Where can you save it?**
- **A database** (used in production).
- **In-memory (RAM)** — persists as long as the program is running. (We'll use this since we're building a basic chatbot.)

LangGraph provides a built-in in-memory checkpointer called `MemorySaver`.

**Three small changes to the code:**

### Change 1 — Import `MemorySaver`

```python
from langgraph.checkpoint.memory import MemorySaver
```

### Change 2 — Create a checkpointer and pass it when compiling

```python
checkpointer = MemorySaver()

chatbot = graph.compile(checkpointer=checkpointer)   # <-- pass the checkpointer
```

> This tells the graph: "Use this checkpointer to save state between runs."

### Change 3 — Identify each conversation with a `thread_id`

When invoking, pass a `config` that includes a `thread_id`:

```python
thread_id = '1'

config = {'configurable': {'thread_id': thread_id}}

while True:
    user_message = input('Type here: ')
    print('User:', user_message)

    if user_message.strip().lower() in ['exit', 'quit', 'bye']:
        break

    response = chatbot.invoke(
        {'messages': [HumanMessage(content=user_message)]},
        config=config                                        # <-- pass the config
    )

    print('AI:', response['messages'][-1].content)
```

Now the chatbot remembers:

```
User: Hi, my name is Nitish.
AI:   Hello Nitish, nice to meet you.

User: What is my name?
AI:   Your name is Nitish. How can I assist you today?

User: Can you add 10 to 100?
AI:   Yes — 10 + 100 = 110.

User: Now can you multiply the result by 2?
AI:   Sure — 110 × 2 = 220.
```

## 8. Threads and Config

**What is a thread?**

> A **thread** is **one interaction with the chatbot**. Multiple users can talk to the chatbot simultaneously — Nitish, Rahul, Amit, all at once. Each user's conversation is a separate thread, identified by a unique `thread_id`.

**The `config` dict** tells LangGraph which thread the current invocation belongs to. Its shape is:

```python
config = {'configurable': {'thread_id': 'some-unique-id'}}
```

Different `thread_id`s have independent conversation histories — switching the thread_id is like opening a fresh chat.

You can also inspect the saved state of a thread at any time:

```python
state = chatbot.get_state(config)
print(state)
```

This returns the full saved state for that thread — including every message exchanged so far.

## 9. How Persistence Works Behind the Scenes

Walking through what happens when the user has a multi-turn conversation:

1. User: *"Hi, my name is Nitish."* → workflow runs → state at END has 2 messages (Human + AI reply) → **checkpointer saves the state to RAM** keyed by `thread_id`.
2. User: *"What is my name?"* → workflow runs again → LangGraph **does not start fresh** — it goes to the checkpointer, **fetches the saved state** for this `thread_id` (the 2 previous messages), then appends the new HumanMessage to it (thanks to the `add_messages` reducer).
3. The LLM now sees the full history and answers correctly. The new AI message is appended → state now has 4 messages → **checkpointer saves again**.
4. The cycle repeats for every turn.

**Limitation of in-memory persistence:** if the program (kernel) is restarted, RAM is wiped — and so is all the saved state. If you used a database-backed checkpointer instead, the state would survive program restarts. That's why **production chatbots use databases** — e.g., you chat on WhatsApp today, come back Friday, and the bot still remembers what you discussed.

## 10. Quick Revision Summary

**A chatbot in LangGraph** is just a sequential workflow with one node: `START → chat_node → END`, run in a loop.

**The state holds the conversation history:**

```python
class ChatState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]
```

| Choice | Why |
|--------|-----|
| `BaseMessage` (not `str`) | Allows `HumanMessage`, `AIMessage`, `SystemMessage`, `ToolMessage` — all of them inherit from `BaseMessage`. |
| `add_messages` reducer | Built-in, optimized version of `operator.add` for message lists. Use it instead of `operator.add` when appending messages. |

**The big gotcha — invoke resets the state.** Every call to `chatbot.invoke(...)` starts a fresh workflow execution. Without persistence, the chatbot **has no memory** across calls — only within a single invocation.

**The fix — persistence with a checkpointer:**

| Step | Code |
|------|------|
| Import | `from langgraph.checkpoint.memory import MemorySaver` |
| Create | `checkpointer = MemorySaver()` |
| Compile with it | `chatbot = graph.compile(checkpointer=checkpointer)` |
| Pass thread on invoke | `config = {'configurable': {'thread_id': '1'}}` <br> `chatbot.invoke(state, config=config)` |

**Key concepts introduced (full deep-dive in the next video):**
- **Persistence** — saving state across `invoke` calls instead of erasing it at END.
- **Checkpointer** — the component that saves and restores state. `MemorySaver` saves to RAM (lost on restart); production uses database-backed checkpointers.
- **Thread** — one isolated interaction with the chatbot, identified by a `thread_id`. Multiple users / sessions = multiple threads.
- **Config** — a dict passed to `invoke` that tells LangGraph which thread this call belongs to.

**The flow with persistence:**
1. Invoke → checkpointer fetches saved state for this `thread_id` → new message appended via `add_messages` → LLM sees full history.
2. Workflow ends → checkpointer **saves** the updated state back.
3. Next invoke → repeat.

**State inspection:** `chatbot.get_state(config)` returns the entire saved state for a thread.
